# Task 66 — FWER of the conditional null under `max_of_n`, at the N we operate

**Pre-registered before anything ran.**

## 1. The question

Task 65 established that the **rotation** null is calibrated per candidate --
`z = (observed - null mean)/null std` has mean -0.041, std 1.048, and 4.0% of
candidates beyond +/-1.96 -- where the **sign-flip** null sits 1.81 sigma low
with 45% beyond -1.96 and none above.

That makes Task 64's remedy plausible: stop letting the cheap null decide, route
to the conditional one. It does **not** make it established. Per-candidate
calibration is necessary and not sufficient. `max_of_n` over 50 nulls is a
further step with its own behaviour, and Task 64 is the standing demonstration
that a null which looks fine in one measurement can be badly wrong in the gate.

**So: what is the FWER of `rotation` + `max_of_n` at N = 50, under the current
metric?** Task 38's 0.060 was `conditional` + `max_of_n` at N = 10 and predates
the idle charge. Nothing describes what routing would actually produce.

## 2. The measurement

**C = 100 campaigns x N = 50 trials x R = 150 rotations = 755,000 runs.**

| knob | value |
|---|---|
| campaigns `C` | 100 |
| trials per campaign `N` | 50 |
| rotations per candidate `R` | 150 |
| candidates | `NullGenerator(seed=66_001)` |
| dataset | `SyntheticSpec(n_sessions=175, ticks_per_session=390, vol_per_tick=0.15, signal_strength=0.0)` |
| dataset seed | `4_242 + campaign_index` — varies per campaign, as in Task 64 |
| rotation seeds | `800_000 + (campaign*N + trial)*R + r` |
| metric | `score(..., idle_charge=0.18)` |
| correction | `correction.max_of_n(..., b=10_000, seed=17, q=0.05)` |
| accept | `reject AND observed_best > 0` |

**R = 150 and not less, deliberately.** `max_of_n` carries a measured resampling
bias of +0.011 at R = 50 and nothing distinguishable from zero past R = 150. At
q = 0.05 a +0.011 bias is a fifth of the thing being measured. Paying for R = 150
removes a known confound from a measurement whose whole purpose is to find out
whether an unknown one exists.

**C = 100 is a coarse read and is meant to be.** At a true 0.05 it gives a Wilson
interval of roughly [0.022, 0.112] -- enough to separate "near nominal" from
Task 64's 0.0020 or from something badly anti-conservative, and not enough to
pin a value. If the answer lands near nominal, extending C is a later decision
and the harness resumes from what is on disk.

## 3. Runs are in-process, and that is a deliberate substitution

Task 64 and 65 ran every candidate through `RemoteStrategy`, spawning a
sandboxed child per run. Here the strategy is executed in process via
`Engine.for_test`.

**Why it is legitimate.** The sandbox exists to keep *agent-written* code away
from the harness. These candidates are generated by `NullGenerator`, which this
repository wrote. There is nothing to isolate from.

**Why it is safe.** Blotter digests were compared between the two paths on the
first four candidates of the stream and came back **byte-identical**, at a 3.8x
to 5.2x speed difference. `--stage verify` repeats that comparison on a larger
sample and prints it; a single mismatch invalidates the substitution and the
measurement should be re-run remotely at four times the cost.

**What it buys.** 755,000 runs at ~2 s each is over 100 hours. At ~0.25 s it is
roughly 11 hours, which is one night.

## 4. What gets reported — fixed now

1. **`reject_rate`** — campaigns where `max_of_n` rejects.
2. **`accept_rate`** — rejects **and** best observed score positive. The FWER.
3. The **paired contrast** against Task 64: both are C x N = 50 campaigns of 50
   edgeless candidates under the same metric and the same correction, differing
   only in the null. Task 64's sign-flip arm gave 0.0020.

Also recorded as context, not as tests: the p-value distribution, the fraction of
campaigns with a positive best, and unscorable counts.

**What each outcome would mean, stated before the numbers exist:**

- **Near 0.05** — routing is sound, and Task 64's conservatism is a property of
  the cheap null rather than of the correction.
- **Also far below 0.05** — the problem is in `max_of_n` at N = 50, not in the
  null. Routing would not fix it, and the correction itself becomes the subject.
- **Materially above 0.05** — rotation + `max_of_n` over-rejects, which is the
  dangerous direction and would take precedence over everything else in this
  file.
